- **Versioning**: every edit is reversible; who changed what, when  
- **Survey control**: known monuments / GPS control points anchor the system  
- **Conflict handling**: when two sources disagree (assessor map vs field GPS), record both and choose a rule

Triangles help with location and local neighborhood queries; **topology + snapping** make digitization trustworthy.

## Core idea
- Each triangle = a leaf in a Merkle tree  
- Leaf hash covers something like: vertices, triangle ID, parent parcel/zone/utility attribution, maybe revision  
- Root hash = cryptographic commitment to the whole county (or bbox) mesh state  
- On-chain: store roots, ownership/rights, and succinct proofs  
- Off-chain or lightly on-chain: geometry editing, triangulation, validation

## Why triangles help on-chain
Blockchains are bad at heavy geometry, good at:
- commitments (Merkle roots)
- membership proofs (“this triangle is in the committed mesh”)
- state transitions with verifiable checks

If every authoritative region is a set of triangles, then:
- a parcel = set of triangle IDs + Merkle proofs
- a utility segment = ordered constrained edges / adjacent triangle references
- a transfer/edit = update leaf set → new root

## Non-overlapping as the key invariant
Your “simple logic” is the trust anchor. At minimum, a valid state should prove:

1. **Coverage**: triangles cover the claimed domain (county and/or bbox exterior, as designed)
2. **Non-overlap**: no two triangles share interior area
3. **Boundary consistency**: shared edges match (especially parcel boundaries / utility constraints)
4. **Attribution exclusivity**: a triangle belongs to at most one parcel (or has explicit layered rights)

On a chain, you usually don’t re-check all geometry every time. You check that a proposed update preserves these invariants relative to the previous root.

## Sensible blockchain architecture (broad)

### Layer 1 — Geometry commitment
- Merkle tree over triangle leaves
- Optional second tree over “features” (parcel → triangle set, utility → edge set)
- Publish root on-chain

### Layer 2 — Rights / records
- Parcel ownership, easements, utility operator rights
- Point to triangle-set commitments, not full polygons

### Layer 3 — Update transactions
Examples:
- Digitize/split a parcel
- Move a boundary
- Add a utility line
- Transfer ownership

Each transaction includes:
- old root
- new root
- proofs of affected leaves
- a validity proof that the local edit preserves non-overlap / topology rules

### Layer 4 — Dispute / audit
- Anyone can verify a parcel claim against the root
- Challenger can submit a conflicting triangle/overlap proof
- Keeps the system “reliable” without trusting one GIS vendor

## What should stay off-chain
Doing full triangulation and continuous digitizing UX fully on-chain is usually too expensive/slow.

Better split:
- **Off-chain:** CAD/GIS editor, snapping, remeshing, generating proofs  
- **On-chain:** roots, ownership, approvals, dispute resolution, verified state transitions  

This is the same pattern as many verifiable data systems: heavy work off-chain, integrity on-chain.

## Merkle design choices (important early)
Decide what a leaf hashes:
- canonical vertex coordinates (lon/lat with fixed precision)
- sorted vertex order / orientation
- adjacent edge IDs
- feature tags (parcel ID, zone ID, utility ID)
- version / timestamp

Fixed precision matters: floating-point ambiguity can break hashes and “non-overlap” checks.

## Proving non-overlap “simply”
There are two levels:

**Local/simple (practical first):**  
- Require a deterministic triangulation algorithm  
- Require shared-edge matching  
- Prove updates only touch a region, and that region’s remesh is valid  
- Use challenges for global disputes

**Strong/global (harder):**

That design is solid: **cheap verification, structured updates, Merkle membership**. The trick is to restrict edits to a tiny set of local operations whose correctness is obvious from a few hashes and coordinates.

## Leaf definition
A leaf commits to:
- 3 vertices in **canonical order** (e.g. sorted by `(x,y)` then oriented CCW as a tie-break, or always sorted then store orientation bit)
- **payload/data** bound to that triangle

So:
`leaf = H(canon(p1,p2,p3) || data)`

Fixed coordinate precision is essential so everyone hashes the same bytes.

## Keep the update algebra tiny
Don’t allow arbitrary remeshing on-chain. Allow only a few **local rewrite rules**.

### Op A — Split triangle by corner + opposite-edge point
Input:
- existing triangle `T = (A,B,C)`
- chosen corner, say `A`
- point `P` on opposite edge `BC`

Output:
- `T1 = (A,B,P)`
- `T2 = (A,P,C)`
(or the analogous pairs for other corners)

Verifier checks, trivially:
1. Merkle proof that old leaf `T` exists under old root
2. `P` lies on segment `BC` (within fixed epsilon / exact rational grid)
3. `P` is strictly between `B` and `C`
4. Canonicalization of `T1`, `T2` is correct
5. New root replaces one leaf with two children via standard Merkle update proof
6. Payload rule: inherit / split / clear data according to your policy

This is ideal: geometry check is local, Merkle check is standard, non-overlap is automatic because you’re only subdividing area you already owned.

### Op B — Attach/update data on a triangle
Input:
- triangle leaf
- new data
- authorization (owner key / capability)

Verifier checks:
1. Merkle proof of old leaf
2. New leaf = same geometry, new data
3. Signature / permission
4. Merkle update to new root

No geometry risk.

### Later ops (still local)
- **Merge reverse-split**: only if two triangles were produced by a prior split and share the interior edge
- **Insert vertex on shared edge**: split both adjacent triangles consistently
- **Edge flip**: optional, harder; avoid initially

Starting with **split + data-update** already supports progressive digitization: digitize by refining triangles where boundaries/utilities need detail.

## Verifier-trivial, prover-friendly
You want:

| Role | Should do |
|---|---|
| Verifier | Check a few equalities, on-segment test, Merkle path, signature |
| Prover | Build proofs, canonicalize points, compute new root, maybe digests |

### Make verification trivial
Package each transaction as:
- old root, new root
- touched leaf opening(s)
- Merkle authentication paths
- op type + parameters (`corner`, `P`, new data)
- signature

Verifier logic stays O(log n) hashes + O(1) geometry.

### Make proving easy in practice
Even if “in theory prover can work hard,” optimize the common path:

1. **Store adjacency off-chain**  
   Triangle ID → 3 neighbor IDs / edge keys. Split then becomes pointer rewrites.

2. **Use an incremental Merkle tree**  
   Prover updates only the path(s) for replaced leaves. No full rebuild.

3. **Deterministic canonicalization library**  
   One shared function for point quantization + triangle ordering. Most prover bugs come from this.

4. **Precompute edge keys**  
   Edge `BC` identity lets you validate “`P` on opposite side” and later shared-boundary edits.

5. **Batch splits**  
   One transaction can include a sequence of splits for digitizing a polyline, each still locally checkable.

6. **Keep data separate if needed**  
   Geometry tree + data tree (same triangle IDs) can make “data-only updates” cheaper and clearer.

## Non-overlap becomes an invariant of the op set
If the initial mesh is a non-overlapping partition, and the only geometry mutation is **split** (and carefully controlled merge), then:

**non-overlap is preserved by construction**

Verifiers don’t need a global non-overlap proof every time. They only need:
- initial trusted/root setup was a valid partition
- each update is a legal split/data op

That’s the practical answer to “simple non-overlapping logic.”

## Suggested transaction types (v1)
1. `SplitTriangle(triangle_id, corner, point_on_opposite_edge)`
2. `SetTriangleData(triangle_id, data)`
3. `TransferRights(...)` on data/ownership
4. Maybe later: `MergeSplitPair(...)` reverse of a recorded split

- Parcel = set of triangle leaves (or root of a subtree/set commitment over those leaves)
- Utility line = ordered sequence of edge splits / constrained edges between triangle vertices
- Every refinement is chain-verifiable with trivial checks

ASSISTANT:
Yes — **time-varying boundaries** are one of the hardest practical issues, and places like Louisiana make that obvious: coastal loss, river migration, water boundaries, elongated/thin geometries, and frequent resurvey/redefinition.

If the system only stores “the current map,” it fails the usefulness test for disputes and audit. It needs **history as a first-class feature**.

## Core design stance
Don’t overwrite boundaries.  
Treat every accepted mesh root as a **version of spatial truth at a time**.

- Root \(R_t\) = committed map at time \(t\)
- Parcel/utility claims are always relative to a root (or a time interval)
- Boundary change = transaction from \(R_t\) → \(R_{t+1}\), not silent edits

Then queries become:
- “As of today, which parcel contains this point?”
- “As of 2019-06-01, which parcel contained it?”
- “When did this triangle stop belonging to parcel X?”

## Why thin / changing Louisiana geometries matter
They stress several assumptions:

1. **Thin corridors / spidery polygons**  
   Tiny numeric errors can flip side-of-edge tests. Fixed precision and robust “on-edge / split” rules matter more.

2. **Land disappears or appears**  
   Coastal erosion/accretion is not just attribute change; the **domain itself** changes. Triangles may need retirement (now water) or addition (new fill/accretion), not only splits.

3. **Legal boundary ≠ visible shoreline**  
   Digitized coastlines can move while legal descriptions lag, or vice versa. The system should allow multiple layers:
   - legal parcel boundary
   - physical shoreline observation
   - administrative parish boundary  
   each with prover authority and effective dates.

4. **Disputes are temporal**  
   Encroachment/title/permit questions are often “who had what *then*?”

## Practical model for boundary change over time

### 1. Versioned roots
Keep an append-only sequence of Merkle roots with timestamps and prover identity.

### 2. Effective-time on features
Parcel membership / utility attributes carry:
- `valid_from`, `valid_to` (or “until next change”)
- authority source
- reason code (`resurvey`, `court_order`, `coastal_loss`, `subdivision`, `easement`)

### 3. Geometry ops beyond simple split
For real boundary evolution you’ll eventually need:
- **split** (refinement/digitization)
- **reassign** triangle from parcel A → B (boundary move)
- **retire** triangle from land domain (inundation)
- **introduce** triangle into domain (accretion/fill), carefully authorized
- maybe **merge** only as reverse of recorded splits

Boundary move in a Merkle-triangle world is often:
refine near the boundary → reassign leaf data along the affected strip.

### 4. Dual answers for “what is here?”
Support both:
- **current operational map** (for permitting/field work)
- **historical legal map** (for title/dispute)

Those can diverge intentionally in coastal zones.

## Verification implications
Verifiers still stay cheap if updates are local and typed:
- prove old leaf set under \(R_t\)
- prove op legality (split / reassign / retire)
- prove authorization for that change class
- publish \(R_{t+1}\)

End users verifying a historical query get:
- the root used for that date
- Merkle proof of triangle + data at that root

## Policy issues (as important as geometry)
Especially in Louisiana-like settings, decide up front:

- Who may declare land→water retirement?
- Is shoreline observational data advisory or authoritative?
- Do parish/county administrative boundaries version separately from parcels?
- On conflict, which layer wins for which application (tax vs navigation vs ownership)?

Without those rules, the chain just immutably stores disagreement.

## Bottom line
Temporal boundary change doesn’t break the triangle/Merkle approach — it tells you the product must be:

**a versioned, attributable spatial ledger**, not a single static cadastral map.

Thin and shifting Louisiana geographies are a strong motivating case: if the system can handle elongated shapes, shoreline retreat, and “as-of-date” parcel queries there, it’s solving something a normal GIS usually does poorly across organizations.

Next useful planning step (still no code): define the **change taxonomy** — subdivision, boundary agreement, court update, coastal loss, accretion, utility as-built — and which prover role is allowed to submit each.
